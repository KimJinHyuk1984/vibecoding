# 3회 운영 메모 — 일하는 동아리 자동 비서

기준은 plan2.md의 새 3회다. 이전 11개 계획의 일정 자동화와 문서 생성을 하나의 흐름으로 합쳤다. 과거 게임 랭킹 3회 메모와 구분한다.

## 수업 목표와 제작 방식

활동 한 건을 입력하면 일정으로 연결되고, 나중에 사람이 남긴 활동 결과가 Docs 보고서와 PDF로 이어지는 도구를 만든다. 한 폼 응답은 참가자 한 명이 아닌 동아리 활동 한 건이다. 참가자마다 같은 행사 일정을 생성하는 구조로 혼동하지 않는다.

이번에는 Forms와 Sheets를 입력·관리 화면으로 사용한다. 새 index.html이나 웹 앱 배포가 필요하지 않은 시트 바운드 Apps Script 프로젝트다. 학생은 Code.gs 전체를 AI에게 직접 요청한다. 교사 완성 코드를 제공하거나 특정 코드 줄 수정을 요구하지 않는다.

1. 로컬 모의 체험에서 직접 실행·자동 실행·중복 방지·PDF 실패 복구를 비교한다.
2. 새 활동 신청 폼과 연결 시트를 준비하고 첫 응답을 제출한다.
3. AI에게 맞춤 메뉴와 관리 열 준비 코드를 요청한다.
4. 메뉴로 선택한 활동의 일정 하나를 만들고 실제 날짜·시간을 확인한다.
5. 설치형 시트 폼 제출 트리거로 새 응답의 일정만 자동 생성한다.
6. 사람이 실제참여인원·한일·느낀점을 기록한다.
7. AI에게 Docs 양식 문구를 요청해 원본 문서를 만들고, 코드로 사본에 내용을 채운다.
8. 완성 문서를 PDF로 저장한다. 반복 실행·수정 버전·일부 실패를 구분한다.
9. 확인한 버전과 설정을 보관하고 연습 트리거를 중지한다.

프롬프트는 기본 7개, 시간 기반 점검 선택 1개, 도움 1개다. 01·02·05·06은 발표에서 두 조각으로 나누되 어느 복사 버튼도 원문 전체를 복사한다. 중간 성취 기준은 v1 메뉴로 일정, v2 폼 제출 자동화, v3 문서·PDF다. 수업 시간을 고정하지 않는다.

## 교실 준비

- 학교 계정의 AI·Forms·Calendar·Apps Script·Docs·Drive 이용 가능 여부를 사전 확인한다.
- 팀 담당자 한 명이 새 시트·캘린더·원본·결과 폴더를 만들고 권한을 승인한다. 담당자가 해당 자원에 접근할 수 있어야 한다.
- 폼 질문은 `활동명`, `활동 날짜`, `시작 시각`, `종료 시각`, `장소`, `계획한 일`이다. 계획만 장문형이고 나머지는 단답형, 모두 필수다.
- 날짜 입력은 YYYY-MM-DD, 시각은 24시간제 HH:mm이다. 같은 날 끝나는 활동으로 한정한다. 폼·서버에서 실제 날짜와 시간 범위를 검증한다.
- 응답 시트의 하단 탭 이름을 `신청`으로 바꾼다. 원래 응답은 보존하고 오른쪽에 관리 열을 추가한다. 직접 정렬·행 삭제 대신 원본을 유지하며 진행한다.
- 이름·학번·명단·이메일은 수집하지 않는다. 예시는 제목에 `[연습]`을 붙인 모의 활동이다. 미래 일정에 가상 활동 결과를 기록하는 경우에도 실제 수행 결과로 제출하지 않는다.
- 프로젝트·시트·연습 캘린더 시간대는 모두 Asia/Seoul로 맞춘다.

| 스크립트 속성 | 입력할 값 |
| --- | --- |
| SHEET_URL | 새 활동 관리 스프레드시트 전체 주소 |
| CALENDAR_ID | 연습 캘린더 설정 → 캘린더 통합의 ID 전체. 브라우저 주소나 비공개 iCal 주소가 아님 |
| TEMPLATE_URL | 보고서 원본 Docs 전체 주소 |
| OUTPUT_FOLDER_URL | 완성본을 담을 Drive 폴더 전체 주소 |

학생이 URL에서 ID를 추출하거나 코드의 주소를 바꾸지 않도록 한다. 필요한 ID 추출은 생성 코드가 수행한다. 시트 주소는 처음, 캘린더 ID는 일정 단계, 나머지는 보고서 단계에서 설정한다. 이전 단계의 설정을 유지한다.

## 기술 확인 사항

| 기능 | 생성 코드에서 확인할 내용 |
| --- | --- |
| 시트 메뉴 | 시트에서 연 바운드 스크립트의 onOpen은 메뉴만 추가한다. 권한이 필요한 Calendar·Drive 작업을 단순 onOpen에 넣지 않는다. 코드 저장 후 시트 새로고침으로 메뉴를 갱신한다. |
| 행 선택 | 수동 메뉴만 활성 시트·선택 행을 사용한다. 제목·빈 행·다중 행·다른 탭 선택은 거절하고 안내한다. 고정 열 번호보다 헤더 이름을 기준으로 관리 열을 찾는다. |
| 관리 준비 | 기존 응답·값·활동번호를 보존한다. 준비를 반복해도 열과 번호가 늘어나지 않아야 한다. 활동번호는 행 번호와 별개의 안정적인 식별자다. |
| 시간 | 명시적인 Asia/Seoul 기준으로 날짜와 시각을 합친다. Sheets가 날짜·시간을 Date나 숫자로 저장하는 경우를 처리한다. UTC 변환이나 표시 문자열의 로케일 추정으로 날짜가 달라지지 않도록 한다. 잘못된 날짜의 자동 보정도 역변환 비교 등으로 거절한다. |
| 일정 | CalendarApp로 지정 캘린더에 등록한다. 저장한 CalendarApp 일정 ID는 REST API의 이벤트 ID와 혼용하지 않는다. 활동번호를 먼저 확정하고 일정 설명에도 남긴다. 초대자나 메일 발송 기능은 추가하지 않는다. |
| 재실행 | script lock 등으로 동일 활동 처리를 직렬화한다. 일정 ID가 없는 경우에도 활동번호로 기존 생성 여부를 확인한다. 생성 후 시트 기록 전 실패처럼 결과가 불확실하면 확인 필요 상태로 멈춘다. 단순히 ‘ID가 없으니 새 생성’으로 구현하지 않는다. |
| 제출 트리거 | 시트용 설치형 폼 제출 이벤트의 range 등으로 새 응답 행을 식별한다. Forms용 이벤트의 response와 혼용하지 않는다. 자동 실행에서 활성 셀·팝업에 의존하지 않는다. |
| 권한·실행자 | 설치형 트리거는 설치자의 계정 권한으로 실행한다. 메뉴 실행자와 자동 실행자가 달라지면 자원 접근 범위도 달라질 수 있다. 팀 담당자 한 명으로 실습한다. |
| 원본 양식 | DocumentApp로 원본 사본을 열어 치환한다. 한 탭의 본문만 사용하는 양식이다. 표시칸의 중괄호는 replaceText의 정규식 메타문자와 구분해 안전하게 처리한다. 원본을 수정하지 않는다. |
| 값 채우기 | 표시칸 열 개를 모두 처리한다. 0명과 빈 인원을 구별한다. 한일·느낀점의 줄바꿈·특수문자를 데이터로 보존하고 비어 있는 내용을 생성하지 않는다. |
| 버전 | 동일 입력은 같은 문서 버전을 사용한다. 결과가 바뀌면 새 버전·입력 스냅샷을 남기고 이전 파일을 보존한다. 파일 이름만으로 충돌을 추정하지 말고 활동번호·버전·저장한 파일 ID를 함께 관리한다. |
| PDF | 완성 문서를 저장·닫은 뒤 그 문서를 application/pdf로 변환한다. 원본 양식을 PDF로 변환하지 않는다. 현재 버전의 문서와 PDF가 함께 확인된 후에만 완료로 표시한다. |
| 일부 실패 | Docs 성공·PDF 실패를 구분한다. 재실행은 기존 문서를 재사용한다. 생성이 불확실하면 같은 버전의 파일을 조회하고 확인 필요로 멈추며 중복 생성을 피한다. 기존 PDF의 내용을 문자열 setContent로 덮어쓰는 방식은 사용하지 않는다. |
| 시간 기반 선택 | processPendingActivities는 빈 상태·미등록이면서 일정 ID가 없는 행만, 실행당 최대 10건 처리한다. 오류·확인 필요를 무한 재시도하지 않는다. 기존 검증·중복 방지 경로를 재사용한다. |

여러 Google 서비스에 걸친 작업 전체가 하나의 원자적 트랜잭션인 것은 아니다. 잠금만으로 외부 서비스 생성 후 실패까지 모두 해결됐다고 설명하지 않는다. 먼저 기록한 활동번호·버전, 단계별 결과와 저장된 ID, 기존 결과 조회, 불확실할 때 중지가 함께 필요하다.

## 실제 계정에서 실행할 확인 항목

1. 메뉴를 두 번 준비해도 원래 응답·번호·관리 열이 보존된다.
2. 16:00~17:00 신청의 실제 Calendar 날짜·시간·장소가 동일하다. 같은 활동 재실행과 수동·자동 동시 실행에서도 일정은 하나다.
3. 새 폼 응답은 자동 실행되고, 기존 셀 편집·코드로 행 추가는 폼 제출 테스트로 착각하지 않는다.
4. 종료≤시작, 없는 날짜, 누락 필드를 거절한다. 트리거 실패가 실행 목록과 행의 오류 상태에 남는다.
5. 실제참여인원 빈칸·음수·소수와 빈 결과로 보고서를 만들지 않는다. 0명은 유효한 숫자로 구분한다.
6. 원본 표시칸은 보존되고 사본에는 시트의 정확한 내용이 들어간다. 특수문자·여러 줄 결과도 확인한다.
7. PDF를 직접 열어 모든 페이지의 한글·내용·버전·잘림을 확인한다. 링크 존재만으로 성공 처리하지 않는다.
8. 동일 입력 반복 시 같은 버전의 Docs 하나·PDF 하나다. 결과 변경 시 새 버전이 생기며 옛 버전은 남는다.
9. 교사가 격리한 연습 사본에서 PDF 단계 실패를 유도해 Docs 재사용과 재시도 결과를 확인한다. 학생에게 코드 줄을 찾아 고치게 하지 않는다.
10. 수업 후 설치한 제출·시간 기반 트리거를 삭제하면 새 자동 실행은 멈추고 이미 만든 일정·파일은 유지된다.

## 시간 기반 선택 미션의 진행

제출 트리거가 계속 켜져 있으면 미등록 신청이 바로 처리되어 시간 기반 차이가 보이지 않을 수 있다. 선택 실습에서는 제출 트리거를 잠시 삭제한 뒤 새 폼 응답 한 건으로 미등록 행을 준비한다. processPendingActivities를 수동 시험한 후 새 미등록 행을 넣어 10분 간격 트리거를 확인한다. 정각·초 단위 실행을 약속하지 않는다. 끝나면 시간 기반 트리거를 삭제하고 필요할 때만 제출 트리거 하나를 다시 설치한다.

## 로컬 체험과 실제 도구의 구분

club-lab은 브라우저 메모리의 신청·일정·문서·PDF 상태를 바꾸는 모형이다. 실제 폼 제출, Calendar 호출, Docs 생성, PDF 변환, 다운로드를 수행하지 않는다. 파일 개수는 상태를 설명하는 숫자다. 중복 방지·실패 재시도 규칙을 이해하기 위한 도입이며 실제 계정 실습을 대체하지 않는다.
