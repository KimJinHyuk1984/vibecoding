# 2회 운영 메모 — 우리 학교 축제 운영 서비스

계획: plan2.md의 새 2회. 이전 11개 계획의 2회 예약과 3회 대시보드를 같은 프로젝트로 묶었다. 이전 게임 꾸미기 2회 메모와 구분한다.

## 목표와 흐름

학생은 코드를 읽지 않는다는 전제를 유지한다. 교사가 제공하는 완성 Code.gs 없이, 자기 HTML을 AI에게 주고 저장 코드를 요청한다. 생성 결과는 전체 파일 단위로 붙여넣고, 실제 화면과 시트에서 확인한다.

1. 마지막 한 자리 체험으로 관심 표와 예약 수를 구분한다.
2. Google Forms의 객관식 질문 하나를 만들고 실제 응답을 새 시트에 연결한다.
3. 가상 예약 화면을 만든 뒤 같은 화면에 실제 저장을 연결한다.
4. 예약 취소·정원·중복 신청 규칙을 확인한다.
5. 같은 시트의 설문과 예약을 집계하는 대시보드를 추가한다.
6. 친구 테스트, 버전 보관, 제작 기록으로 마무리한다.

기본 프롬프트 7개, 선택 검색·정렬 1개, 문제 해결 1개. 긴 03·06 프롬프트는 발표에서 두 조각으로 나누지만 어느 조각의 복사 버튼도 전문을 복사한다. 고정 수업 시간은 두지 않는다. v1 화면 연습, v2 실제 예약, v3 취소·현황을 중간 성취 기준으로 사용한다.

## 계정과 시트 준비

- 학교에서 허용한 AI·Forms·Apps Script 환경을 사용한다. 실제 학생 계정에서 접근 가능 여부와 웹 앱 실행 범위를 사전 확인한다.
- 1회와 다른 새 채팅·프로젝트·시트를 사용한다. 한 팀은 같은 설문과 앱 주소로 공동 테스트한다.
- 설문 질문은 `가고 싶은 부스`, 선택지는 `방탈출`, `인생네컷`, `미니게임`으로 고정한다. 객관식 필수 질문이다.
- Forms 응답 저장 위치를 새 스프레드시트로 연결하고 아래 응답 탭을 `설문 응답`으로 바꾼다. 시트 파일 이름과 탭 이름을 구분한다.
- 실습은 실명·학번·연락처·이메일을 수집하지 않는다. 학교 범위로 게시하고 응답자용 링크를 안내한다.
- 같은 시트에서 새 Apps Script 프로젝트를 열고 `Code.gs`와 소문자 `index.html`을 붙인다. `SHEET_URL` 스크립트 속성에 전체 시트 주소를 넣는다.
- `부스`·`예약` 탭은 AI 생성 서버가 처음 사용할 때 만든다. 이미 존재하면 보존해야 한다. 설문 응답 탭과 헤더도 보존한다.
- 웹 앱 `/exec`에서 저장을 확인한다. 수정은 파일 저장뿐 아니라 기존 배포의 새 버전 반영까지 한다.

## 교사용 기술 확인

학생용 프롬프트는 요구사항을 일상어로 표현한다. 아래 항목은 생성된 코드의 동작을 교사가 확인할 때 참고한다.

| 기능 | 기술과 확인 기준 |
| --- | --- |
| 화면·서버 | HTML Service, google.script.run의 비동기 성공·실패 처리. 서로 다른 생성 단계의 함수·인자·응답 구조가 일치해야 한다. 별도 외부 HTML에서 Sheets로 직접 쓰는 구조를 혼합하지 않는다. |
| 저장 | SpreadsheetApp로 SHEET_URL의 시트를 열고 부스·예약을 관리한다. Date를 클라이언트에 반환할 때는 문자열로 변환하는 등 전달 가능한 자료형을 사용한다. |
| 입력 | 서버에서도 별명 한글·영문·숫자 2~12자와 허용된 부스를 확인한다. 화면 검증만으로 끝내지 않는다. |
| 정원 | 웹 앱에서는 LockService의 script lock 등으로 활성 예약 재조회·정원 확인·기록을 같은 임계 구역에서 처리한다. 잠금 획득 실패는 성공으로 응답하지 않는다. 취소도 같은 규칙으로 처리하고 완료 전 쓰기를 확정한다. |
| 중복 | 같은 신청의 요청 식별자를 재시도에도 유지한다. 중복 식별자에 같은 내용인지 확인한다. 새 신청과 재시도는 구별한다. 저장 성공 뒤 현황 조회 실패가 재저장으로 이어지지 않아야 한다. |
| 취소 | 예약번호와 충분히 추측하기 어려운 확인문자를 서버에서 검증한다. 취소 상태·시각을 기록하며 행은 보존한다. 반복 취소로 가용 좌석이 증가하지 않아야 한다. |
| 정보 범위 | 공개 현황 API는 집계만 반환한다. 전체 명단·다른 예약의 번호·취소 확인문자를 HTML에 숨겨 전달하는 것도 피한다. 화면에서 안 보이는 것과 서버에서 보내지 않는 것은 다르다. |
| CRUD | 생성·조회·수정을 체험한다. 삭제 개념은 설명하지만 취소는 물리 삭제 대신 상태 변경으로 구현한다. |
| 집계 | 설문은 지정된 질문과 부스 이름에 해당하는 유효 응답만 센다. 예약은 활성 상태만 센다. 관심 비율 분모는 유효 설문 전체, 예약률 분모는 부스 정원이다. 취소가 설문 표를 줄이지 않는다. |
| 빈 값·실패 | 응답 0개와 탭·헤더 누락, 통신 실패를 구별한다. 실패를 0으로 표시하지 않는다. 설문 갱신은 현황 새로고침으로 읽으며 자동 실시간 동기화로 설명하지 않는다. |

별명은 본인 인증이 아니다. 이 수업은 1인 1예약, 결제, 로그인·관리자 인증을 구현했다고 주장하지 않는다. 운영자는 원본 시트에서 기록을 확인하고 공개 웹 현황에는 집계만 표시한다. 실제 행사 운영 전 필요한 계정·권한·부하 검토는 별도 범위다.

## 실제 생성 앱에서 확인할 시나리오

- 설문 응답 3개 → 시트의 3줄 → 대시보드의 부스별 숫자가 일치한다.
- 빈 별명, 허용되지 않는 문자, 선택하지 않은 부스로 신청할 수 없다.
- 정원 2명에 활성 예약 1명인 부스에 두 기기에서 동시에 신청해 한 명만 성공한다.
- 같은 신청을 여러 번 클릭하거나 응답 지연 뒤 재시도해도 한 줄만 저장된다.
- 틀린 확인문자는 취소하지 않는다. 맞는 값은 한 번 취소하며 반복해도 자리가 더 늘지 않는다.
- 새로고침 후 실제 저장된 예약을 읽는다. 이미 성공한 저장을 현황 읽기 실패 때문에 다시 생성하지 않는다.
- 취소 후 예약 수·예약률은 줄고 관심 표는 그대로다. 동점 순위가 같고, 응답 0개도 나눗셈 오류가 없다.
- 처음 생성·업데이트·재배포가 기존 설문·예약 기록을 지우지 않는다.

위 목록은 학생별 AI 생성 앱의 현장 검증 항목이다. 강의 사이트 브라우저 검증 통과와 구별한다.

## 체험 위젯과 수업 구분

강의 페이지의 festival-lab은 로컬 메모리의 관심 표·예약 수로 규칙을 체험한다. ‘마지막 자리 · 2명 신청’은 올바른 처리 결과를 설명하는 시뮬레이션이며 서버 동시성의 증명이 아니다. 새로고침·체험 초기화로 예시 상태로 돌아가며 Forms나 Sheets에 쓰지 않는다. 생성 앱의 실제 동시 접속은 위 시나리오로 별도 확인한다.
